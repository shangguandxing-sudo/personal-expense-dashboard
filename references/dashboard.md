# 运行与验证

## 本机启动

1. 复制 [assets/dashboard](../assets/dashboard/) 到使用者自己的目录。保留 `vendor` 及其许可证。
2. 在复制的目录中运行下列命令，用浏览器打开 `http://127.0.0.1:8765/`。

   ```sh
   python3 -m http.server 8765 --bind 127.0.0.1
   ```

3. 第一次可点「查看示例」，也可以从「批量导入」选择 [虚构样例](../assets/examples/) 的四个文件。导入样例后点击「清除筛选」看全历史。确认付款 **¥178.00**、到账退款 **¥45.00**、净支出 **¥133.00**。
4. 用真实文件时，改用独立的浏览器配置或不同测试端口，防止虚构数据混进正式账本。真实记录只导入属于各自使用者的本地实例。浏览器 IndexedDB 按来源地址分区。保持同一浏览器与相同的协议、主机、端口，才能继续使用原来的导入记录。原始账单另行留存，便于恢复。
5. 关闭本地服务后，下次用相同目录和端口启动即可。压缩包可共享模板与样例。个人账单和浏览器存储从使用者本机开始建立。

本地模板使用打包的解析库，可读 CSV、TXT、XLSX、XLS 和包含这些表格的 ZIP。加密 ZIP 在浏览器本地输入解压密码。模板不会直接解析银行 PDF，也没有自动登录、订单抓取、云同步。先将银行或截图数据整理成可核对的表格再导入。

## 输入要求

- 支付流水表格至少提供交易日期、金额、足以判断收支与类型的列，并尽量包含交易对方、商品说明、状态、支付方式、交易号和商户单号。支付宝与微信文件名保留对应渠道名。表头前的说明行可以保留，UTF-8、带 BOM 的 UTF-16 和 GB18030 文本可识别。导入后查看跳过、异常和重复统计。
- 银行流水表使用独立文件名，例如 `银行卡-消费流水.csv`。文件中的交易号和商户单号按原含义填写，若尚未复核银行卡与支付平台重叠，可先单独导入到测试实例。通用模板会根据唯一且同向同额的支付引用抑制已确认重复的银行卡行，同日同额但无共同引用不会自动扣除。特定银行的固定卡片尾号和 PDF 映射需要按使用者实际账单另行适配。
- 订单附件的文件名带平台名，例如 `美团-订单.csv` 或 `拼多多-订单.csv`，用「下单时间、订单实付总额、店铺名称、商品名称、规格、数量、订单号、订单状态」等表头。每个商品一行，同一订单各行重复填整单实付。商品相同且规格相同的行先合并数量。只有能核实支付记录的商户单号确实对应平台订单号时，才可共用那个引用。模板只按同平台订单号补明细，无法匹配的订单不增加支出。
- 旧账本迁移前保留原始导出与用户更正。交易号长度超过电子表格精度时从带文本编号的原始文件重取，不能用已经凑整的长数字补关联。跨币种或多个同渠道账号需要扩展来源键和币种口径再合并，通用模板默认单渠道单账本口径和人民币。

## 功能验收

- 指标区展示实付、到账退款和净支出，月度看板与日、周、月、季度、年趋势使用同一筛选结果。周从周一开始。
- 时间范围支持全部、年、季度、月和自定义区间。全局筛选置顶，渠道、平台、商户或品牌、消费类别可多选。每个维度内部取并集，不同维度取交集。
- 可以隐藏已成对的全额退款，切回可查看原始行。示例中隐藏 ¥30.00 的全额退款后，全历史仍为 ¥133.00，部分退款 ¥15.00 仍可见。明细在固定高度内滚动，支持金额排序、搜索、只看待补商品。点击交易核查证据和订单商品，编辑分类后重新打开复核。
- 在浏览器核对「导入 → 总额 → 多选 → 明细 → 改类 → 重新打开」全流程。按来源抽查至少一条普通付款、一条退款和一条多商品订单。没有可用浏览器时，运行下列计算样例并说明界面验证情况。

   ```sh
   node scripts/verify-example.mjs
   ```

如需改变标签规则，查看模板 `ledger.mjs` 的 `platforms`、`merchantBrands` 和 `classify`，先补具体商品与商户规则，再回归已有分类和待核项目。适配新数据源时优先新增小型格式映射，保留原始字段及可用于追溯的证据。
